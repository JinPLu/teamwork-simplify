# Teamwork Collaborate

Keep the project's goal, decisions and their reasons usable as the work changes.
Infer where to continue from the user's request and existing context; the user
need not supply a workflow prompt. Apply the relevant parts of this method to
the current question, not as a fresh interview or full rewrite on every turn.

## Method

1. **Resume the question the user is asking.** Establish the overall goal,
   settled choices, rejected approaches and unresolved questions from verified
   conversation and project context. Distinguish a new direction from detailing
   an agreed one. Locate the present disagreement or uncertainty: what changes
   depending on its answer? If the user objects, identify which premise, choice,
   consequence or standard of value they are challenging before rewriting the
   recommendation.
   Answer a request to understand the existing design before introducing a
   new choice. Investigate discoverable gaps yourself; do not restart a survey.
2. **Organize the live choices.** For a long discussion, use a visible question
   tree or nested outline in the topic document. Separate necessary parts of
   the goal from alternatives within a part. Expand the active question into
   its meaningful alternatives, supporting reasons, unresolved premises and
   consequences for dependent questions. Mark the current branch and link its
   detailed reasoning. Keep settled and deferred branches with their reasons
   and return conditions. A list of chapter titles is not this decision map;
   update only affected branches, leaving the others available for resumption.
3. **Choose the next move from those relationships.** Follow the user's
   discussion priority, including an unfinished explanation. Otherwise address
   an unresolved premise whose answer
   changes the current choice. Gather facts independently; ask for user
   preferences only where they materially change the outcome. A downstream
   choice can be explored under explicit alternatives, but cannot silently
   settle its unresolved premises. If cost or new evidence makes a different
   discussion order useful, explain what it changes for the original question
   and why it takes priority. A newly found improvement is a proposal, not a
   replacement for the current deliverable. Dependency means an
   influence to reason about, not a blanket stop on investigation or work.
4. **Discuss a concrete trade-off.** Explain the active question in the
   project's own terms, the meaningful options, their evidence, costs and
   consequences, and your recommendation. Distinguish established facts,
   user decisions and your assumptions. Before carrying evidence into a
   comparison, establish which objects each side denotes and whether the source
   result belongs to that side; shared names or dates do not establish the link.
   Do not report a difference across an unverified match. Give the supported
   partial result and identify the unresolved comparison instead.
   Connect references and existing
   implementations to why they apply here: which judgment the evidence supports,
   how far it holds for the present object and conditions, and which choice it
   changes. Group independent user choices;
   defer dependent questions and make routine implementation judgments yourself.
   Continue the conversation from the active branch instead of reciting the
   whole document or substituting an unrelated yes/no question.
5. **Apply changes before continuing.** User feedback, implementation results
   and experiments can change the premises. Distinguish an unchanged goal, an
   invalidated approach and an updated observation; revise the affected judgment
   and its implications for dependent choices and the existing plan.
   Preserve unrelated decisions and authorization. A challenged choice does
   not become settled because an old implementation uses it; a recorded
   recommendation is not user approval. Check the premise that matters now
   before inheriting an old recommendation, without rechecking settled history.
   Reopen only what the change affects. State its consequence and use it to
   choose the next investigation, discussion or authorized action.
6. **Deliver at the requested level.** A discussion can end with a useful
   assessment or decision; a document rewrite must support resuming the actual
   question. When a plan is requested, derive it from the selected branches:
   explain the outcome and approach, concrete changes, inputs and outputs,
   dependencies, material costs and end-to-end verification. Reference the
   topic's maintained judgment rather than duplicating its discussion. Name critical
   files and existing functions to reuse where useful; describe repeated work
   once. Account for every necessary part of the goal and explain unresolved
   or deferred coverage. A local experiment cannot silently replace the full
   deliverable. Keep conditional proposals separate from settled work; host
   permissions and scheduling govern execution.

## Document references

When creating, restructuring or substantively maintaining a discussion document,
read [discussion](references/discussion.md); for a plan, read
[plan](references/plan.md). Use the relevant reference without requiring the user
to name it. Headings and layout are adaptable; the decision relationships must
remain readable. The method above owns how to discuss; references illustrate
what the resulting document contains, not a second workflow.

Other optional outlines: [record](references/record.md),
