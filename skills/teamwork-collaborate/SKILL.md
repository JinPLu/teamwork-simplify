# Teamwork Collaborate

Keep the project's goal, decisions and their reasons usable as the work changes.
Infer where to continue from the user's request and existing context; the user
need not supply a workflow prompt. Apply the relevant parts of this method to
the current question, not as a fresh interview or full rewrite on every turn.

## Method

1. **Resume the question the user is asking.** Establish the overall goal,
   settled choices, rejected approaches and unresolved questions from verified
   conversation and project context. Distinguish a new direction from detailing
   an agreed one. Locate the present disagreement or uncertainty: what changes
   depending on its answer? Answer a request to understand the existing design
   before introducing a new choice. Before proposing a mechanism, parameter or
   evaluation, check the topic's settled boundaries and search the project's
   records for how the relevant references or neighbouring work handle the
   same choice; mark a design without such a source as your own. When the
   user objects, first name in one sentence the premise, choice, consequence
   or standard of value being challenged, then revise only what depends on it.
   Investigate discoverable gaps yourself; do not restart a survey.
2. **Organize the live choices.** For a long discussion, keep a visible question
   tree or nested outline in the topic document. Separate necessary parts of
   the goal from alternatives within a part. Expand the active question into
   its meaningful alternatives, supporting reasons, unresolved premises and
   consequences for dependent questions, and mark the current branch. A list
   of chapter titles is not this decision map. When a decision or result
   changes a branch, rewrite that node (status, choice, next step) in the same
   edit. Fold a superseded option, with any section that argued for it, into
   one line with its reason and return condition; a dated summary beside an
   outdated map, or old sections still marked open, leave it stale.
   Decisions reached in comments, explainer pages or other threads count too.
3. **Choose the next move from those relationships.** Follow the user's
   discussion priority, including an unfinished explanation. Otherwise address
   an unresolved premise whose answer changes the current choice. Gather facts
   independently; ask for user preferences only where they materially change
   the outcome. An untested suspicion is something to check, not an option for
   the user to choose. A downstream choice can be explored under explicit
   alternatives, but cannot silently settle its unresolved premises. If cost or
   new evidence makes a different discussion order useful, explain what it
   changes for the original question and why it takes priority. A newly found
   improvement is a proposal, not a replacement for the current deliverable.
   Dependency means an influence to reason about, not a blanket stop on
   investigation or work.
4. **Discuss a concrete trade-off.** Explain the active question, the
   meaningful options, their evidence, costs and consequences, and your
   recommendation. Distinguish established facts, user decisions and your
   assumptions. Before carrying evidence into a comparison, establish which
   objects each side denotes and whether the source result belongs to that
   side; shared names or dates do not establish the link. Across an unverified
   match, give the supported partial result and leave the comparison open.
   Connect references and existing implementations to why they apply here:
   which judgment the evidence supports, how far it holds for the present
   object and conditions, and which choice it changes. Group independent user
   choices; defer dependent questions and make routine implementation
   judgments yourself. Continue the conversation from the active branch
   instead of reciting the whole document or substituting an unrelated yes/no
   question.
5. **Apply changes before continuing.** User feedback, implementation results
   and experiments can change the premises. Distinguish an unchanged goal, an
   invalidated approach and an updated observation, then reopen only what the
   change affects. Preserve unrelated decisions and authorization. A challenged
   choice does not become settled because an old implementation uses it; a
   recorded recommendation is not user approval, and approving "your
   recommendation" covers only what you stated. Check the premise that matters
   now before inheriting or implementing a recommendation, without rechecking
   settled history. State the consequence and use it to choose the next
   investigation, discussion or authorized action.
6. **Deliver at the requested level.** A discussion can end with a useful
   assessment or decision; a document rewrite must support resuming the actual
   question. When a plan is requested, derive it from the selected branches;
   the decision map and open choices stay in the topic document and the plan
   links them. Account for every necessary part of the goal and explain
   unresolved or deferred coverage. A local experiment cannot silently replace
   the full deliverable. Keep conditional proposals separate from settled work;
   host permissions and scheduling govern execution.

## Document references

When creating, restructuring or substantively maintaining a discussion document,
read [discussion](references/discussion.md); for a plan, read
[plan](references/plan.md), without requiring the user to name them. Headings
are adaptable; the decision relationships must remain readable. References
illustrate what the resulting document contains, not a second workflow.
