# Teamwork 项目文档

这里保存 `teamwork-collaborate` 在讨论、定方向、拆计划、并行执行、整合
验证这条链路上真正需要跨会话复用的东西。文档的目的不是建立另一套工作流
状态机，而是让重要目标、理由、证据、决定和被推翻的方案能够跨任务继续
使用。

## 从哪里开始

1. 直接按下面四个种类目录浏览。
2. 需要追溯某个观点时，阅读专题文档中的带时间历史和它链接的前序记录。

路径形状是 `docs/teamwork/<kind>/<slug>.md`。同一身份复用同一文件。

## 文档类型

| 目录 | 维护的内容 | 建档粒度 |
| --- | --- | --- |
| `discussions/` | 选项、权衡、已定选择、被否决的方案与仍待决定的问题 | 一个持续的决策目标 |
| `plans/` | 已选方向的可执行步骤、依赖、并行线与派发、验证和停止条件 | 一个选定方向 |
| `records/` | 可跨会话复用的结果、结论与阻塞 | 一个值得复用的结果 |
| `experiments/` | 一次试验的说法、设置、实际运行、结果与结论 | 一次可复现的试验 |

## 维护原则

- 每份专题文档顶部维护当前最佳综合，底部按时间追加有意义的演变历史。
- frontmatter 记录 `status`（active / superseded / archived）、
  `superseded-by`、`created` 和 `updated`。
- "当前"只表示现在采用的工作认识，不表示后来观点必然正确。
- 接受文档不原地改写成反转；supersede 时写新文档并保留双向链接。
- 历史观点只做错字、排版或链接修正；观点变化通过新的时间条目说明。
- 追加 History 由写入方直接编辑文件本身，在文档底部追加一条新的时间条目；
  规则是只追加、不改写已有条目。
- 不使用 Case、JSON 索引、文档 schema、迁移状态、向量库或 readiness 作为
  文档维护的前置门。
- Init 不会预先创建空的 `docs/teamwork` 树；目录随首次检查点写文件出现。
